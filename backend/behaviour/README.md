# Поведенческий модуль на Go

Модуль читает историю из PostgreSQL, находит регулярные поступления и привычное время первого трансграничного перевода после них, затем записывает будущие окна в `behaviour_push`. Работает как пакетный CLI и предоставляет API истории знакомого платежа. Рядом запускаются отдельные процессы Pusher и Payment Scheduler.

## Pusher, history API и Payment Scheduler

Подготовить полное синтетическое демо:

```sh
docker compose up -d --wait db
docker compose run --build --rm behaviour demo --as-of 2026-09-01T00:00:00+03:00
docker compose run --build --rm behaviour seed-services
docker compose --profile services up --build
```

Сервисы слушают только localhost: Behaviour API — `8080`, Pusher — `8081`, Payment Scheduler — `8082`. В демо запросы используют заголовок `X-User-ID: demo-regular`; в рабочей системе его должен выставлять доверенный шлюз после аутентификации.

- `GET /api/behaviour/history` возвращает исходный исторический платёж, число прошедших недель, получателя, телефон, банк, страну, назначение, валюты и сумму. Этого контракта хватает для предзаполнения формы.
- `GET /api/notifications` показывает отправленные демо-уведомления пользователя.
- `POST /api/schedules` создаёт подтверждённый ежемесячный платёж; требуется `Idempotency-Key`.
- `GET /api/schedules`, `GET /api/schedules/{id}`, `PUT /api/schedules/{id}` и `DELETE /api/schedules/{id}` управляют расписаниями пользователя.

Pusher сериализует решение блокировкой строки клиента. Сначала он ищет активный поведенческий сигнал, подтверждённый свежим поступлением и отсутствием уже выполненного перевода. Затем рассматривает глобальные сообщения с приоритетом `history`, после них `news`. Запись в `completed_push` занимает один из двух слотов локальной недели пользователя; уникальные ограничения защищают от повторной доставки и гонок между воркерами.

`global_notifications` содержит готовый текст, тип `news` или `history`, время создания, срок жизни и метаданные ML. Две ML-системы в демо представлены одной нодой каждая и работают на явно синтетических Open Data.

Payment Scheduler хранит исходный день месяца, локальное время и IANA timezone. Для коротких месяцев дата сдвигается на последний день, после чего возвращается к исходному числу. Создание требует отдельного `confirmed: true`; повтор запроса с тем же ключом не создаёт дубль. Таблица `scheduled_payment_runs` обеспечивает уникальность одного исполнения на одну запланированную дату.

Транспорт пушей (`demo-inbox`) и исполнение платежей (`demo-ledger`) локальные: внешняя push-платформа и реальное банковское списание не вызываются.

## Запуск демо

Нужен работающий Docker с Compose. Команды из корня репозитория:

```sh
docker compose up -d --wait db
docker compose run --build --rm behaviour
```

Вторая команда выполняет `demo --as-of 2026-09-01T00:00:00+03:00`: создаёт схему, добавляет синтетическую историю и сохраняет прогноз. JSON результата выводится в stdout, сообщения о выполнении — в stderr. БД остаётся работать на `localhost:5433`; порт можно изменить через `BEHAVIOUR_DB_PORT`. Данные хранятся в Docker volume. Учётные данные в Compose предназначены для локального демо.

Демо содержит 64 операции за март–август 2026 года:

- `demo-regular`: поступления 5-го и 20-го в 09:00, переводы RUB → TJS в день поступления или на следующий. Есть неуспешные переводы и внутренние платежи, которые алгоритм исключает.
- `demo-sparse`: два месяца истории, недостаточно для кандидатов.
- `demo-irregular`: переводы через 5–10 дней после поступления, вне выбранной гипотезы о переводе в ближайшие 0–3 дня.

Ожидаемый результат для `demo-regular` на сентябрь:

| Даты | Местное время, Europe/Moscow | Типичная сумма списания | Наблюдения |
| --- | --- | --- | --- |
| 5 и 6 сентября | 17:45–19:15 | 15 500 RUB | 6 из 6 циклов |
| 20 и 21 сентября | 11:40–13:10 | 20 500 RUB | 6 из 6 циклов |

Это **четыре строки-кандидата**, по одной на каждый дневной интервал. Два дня одного зарплатного цикла — альтернативные моменты, а не указание отправить два пуша.

Посмотреть результат в БД:

```sh
docker compose exec db psql -U behaviour -d behaviour -c "
SELECT user_id, cycle_date,
       window_start AT TIME ZONE timezone AS local_start,
       window_end AT TIME ZONE timezone AS local_end,
       typical_amount_minor / 100.0 AS amount_rub,
       source_currency, corridor, sample_count, support_ratio
FROM behaviour_push
WHERE as_of = '2026-09-01T00:00:00+03:00'
ORDER BY window_start;"
```

Деление на 100 в примере относится к RUB. В общей интеграции число младших единиц зависит от валюты.

Повторный запуск не дублирует исходные операции и кандидатов. Остановить контейнер, сохранив данные:

```sh
docker compose stop db
```

## Команды и локальный Go

Доступны `migrate`, `seed`, `analyze`, `demo` (последовательно все три). `seed` добавляет только фиксированную демоисторию и не очищает таблицы. Для своих данных запускайте `migrate` и `analyze`.

```sh
cd behaviour
export DATABASE_URL='postgres://behaviour:behaviour_demo@localhost:5433/behaviour?sslmode=disable'
go run ./cmd/behaviour migrate
go run ./cmd/behaviour seed
go run ./cmd/behaviour analyze --as-of '2026-09-01T00:00:00+03:00' --history-months 6 --horizon-days 30
```

Нужен Go 1.23+. Без `--as-of` используется текущее время. История — предыдущие полные календарные месяцы плюс текущий неполный месяц, горизонт — будущие календарные дни. Выбираются окна, пересекающие `[as-of, as-of + horizon-days)`; начало уже активного окна может находиться до `as-of`.

В Docker свой срез запускается так:

```sh
docker compose run --rm behaviour analyze --as-of '2026-09-05T10:00:00+03:00'
```

## Алгоритм и принятые допущения

1. Для каждого клиента берём только `completed` с `occurred_at < as-of` и `recorded_at < as-of`. Часы и календарные даты считаются в IANA timezone клиента. Поздно загруженная операция не появляется в срезе до момента загрузки.
2. Группируем поступления по исходной валюте и числу месяца. Даты 5 и 20 заданы только в тестовых данных. Несколько поступлений в одну дату считаются одним циклом, начало — первое поступление. Требуются минимум три наблюдаемых цикла и поступления хотя бы в 60% доступных месячных дат. Цикл участвует в обучении только после завершения всех дней 0–3: незавершённый период не считается пропуском перевода.
3. После поступления ищем первый завершённый трансграничный перевод в течение 0–3 календарных дней, отдельно по исходной валюте, валюте получателя и коридору. При нескольких близких датах поступлений перевод относим к последней. Нужны переводы минимум в трёх разных месяцах и как минимум в 60% наблюдаемых циклов.
4. На круговой шкале суток находим самый короткий интервал, покрывающий не менее 80% наблюдаемых времён. Добавляем 30 минут с обеих сторон. Если интервал шире шести часов, кандидата не создаём. Поддерживаются интервалы через полночь. Для покрываемых наблюдений переносим диапазон задержек на будущие даты поступлений; каждый день диапазона получает свой интервал.
5. Типичная сумма — медиана списаний; дополнительно сохраняются P25/P75 методом ближайшего ранга. Деньги хранятся в целых младших единицах исходной валюты, без смешивания RUB и других валют. Сумма поступления не используется как сумма предполагаемого перевода.
6. Пропускаем завершившиеся окна и циклы, в которых уже известен выполненный перевод по тому же коридору в дни 0–3. Для несуществующего числа месяца (например, 31 апреля) прогноз не создаётся.

`support_ratio` — наблюдаемая доля циклов с переводом, **не калиброванная вероятность**. `time_coverage` — доля исторических времён, попавших в выбранный часовой интервал. Они не доказывают точность на будущих данных.

## Контракт данных и результата

- `clients`: обезличенный `user_id` и часовой пояс.
- `transfers`: вид операции (`income`, `cross_border`, `domestic`), статус, время события и время появления в системе, сумма, валюты и коридор. Все виды денежных событий хранятся вместе, чтобы явно связать поступление и перевод.
- `behaviour_push`: клиент, дата среза, версия алгоритма, коридор, дата зарплатного цикла, конкретные `window_start` / `window_end` типа `timestamptz`, timezone, медиана/P25/P75, количество наблюдений, доля циклов и JSON-метаданные с ID подтверждающих переводов и объяснением.

Интервалы полуоткрытые: `[window_start, window_end)`. Срез для одной пары `(as_of, model_version)` целиком заменяется в сериализуемой транзакции: при повторном запуске исчезают и устаревшие кандидаты. Срезы других дат сохраняются. ID строки и `created_at` при пересчёте могут измениться; это не идентификатор доставки. Другие параметры пересчёта сохраняются в metadata. Одновременные запуски сериализуются блокировкой; при конфликте сериализации команда завершится ошибкой, её можно повторить.

Для интеграции выбирайте **один явно заданный актуальный срез** и проверяйте `window_start <= now() AND now() < window_end`. Исторические срезы нельзя суммировать в очередь уведомлений.

## Проверки

```sh
cd behaviour
go test -race ./...
go vet ./...
TEST_DATABASE_URL='postgres://behaviour:behaviour_demo@localhost:5433/behaviour?sslmode=disable' go test -race ./...
```

Без `TEST_DATABASE_URL` интеграционный тест явно пропускается. С ним тест создаёт отдельную временную схему, проверяет миграцию, повторное заполнение, расчёт, сохранение метаданных, отсутствие дублей и удаление устаревших кандидатов. Демоданные основной схемы не затрагиваются.

## Границы реализации

Это объяснимый статистический baseline для запрошенного поведенческого модуля. «Оптимальное окно» здесь означает компактный интервал с высокой исторической повторяемостью. Преимущество над простым правилом, бизнес-эффект и пригодность на реальных клиентах ещё нужно проверять на out-of-time истории и в пилоте.

Календарный паттерн фиксированный: перенос зарплаты из-за праздников, несколько переводов в одном цикле, адаптация к смене поведения и масштабная потоковая обработка пока не реализованы. Прогноз поступления не гарантирует наличие денег на счёте. Модель обрабатывает историю каждого клиента в памяти; для банковского объёма потребуются пакетная обработка и оптимизация поиска событий. Для воспроизводимости предполагается неизменяемая история завершённых операций и timezone клиента; версионирование исправлений статусов и профиля не реализовано.

В соответствии с контекстом PDF статус строки — `candidate`. Проверка текущего курса против исторического, согласие на коммуникацию, frequency cap, тихие часы и повторная проверка уже выполненного перевода должны выполняться следующим decision engine непосредственно перед отправкой. Этот модуль сохраняет временные окна и не отправляет уведомления. Интеграция с существующим веб-прототипом не входит в текущий сценарий.
