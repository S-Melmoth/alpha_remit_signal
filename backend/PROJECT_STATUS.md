# Что сделано в проекте

## Кратко о проекте

Разработан демонстрационный продукт для трансграничных переводов: интерактивный банковский веб-прототип и набор backend-сервисов, которые анализируют платёжное поведение, формируют персональные уведомления, предзаполняют знакомый перевод и позволяют создать регулярный платёж.

Проект работает локально и не выполняет реальные банковские операции. Все пользователи, транзакции, прогнозы, курсы и уведомления в демо являются синтетическими.

## Пользовательский интерфейс

### Лендинг

- Создан адаптивный лендинг «Ближе, чем кажется» в красно-белой стилистике Альфа-Банка.
- Добавлена сетка из пяти продуктовых возможностей.
- Реализовано диалоговое окно выбора между умными сценариями и обычным переводом.
- Добавлены интерактивная композиция карточек, реакция на движение курсора и поддержка `prefers-reduced-motion`.
- Интерфейс адаптирован для настольных и мобильных экранов, включая ширину 320 px.

### Пять продуктовых сценариев

Для каждой возможности создана отдельная интерактивная страница с прототипом телефона, пошаговой демонстрацией, режимами Product/Tech и синтетическими таблицами данных:

1. **Поведенческий пуш** — напоминание в привычное время после фактического поступления денег.
2. **Новостной прогноз** — уведомление на основе синтетического сигнала из открытых данных.
3. **Рекомендательный прогноз** — сообщение на основе анализа исторической динамики курса.
4. **Предзаполнение** — открытие знакомого платежа с уже заполненными реквизитами.
5. **Постоянный платёж** — создание, просмотр, изменение и отмена ежемесячного расписания.

Показанные на этих страницах продуктовые метрики являются частью демонстрационной концепции, а не результатами реального пилота.

### Сценарий трансграничного перевода

- Восстановлены все восемь основных экранов из исходного PDF.
- Реализован путь: платежи → переводы за рубеж → страна → способ → получатель → банк → назначение → сумма → подтверждение.
- Добавлены поиск страны, прокрутка списков и навигация по шагам.
- Поддерживаются демонстрационные переводы в Таджикистан, Беларусь, Кыргызстан и Узбекистан.
- Реализованы ввод и нормализация номера телефона.
- Добавлены проверка суммы, лимитов и доступного баланса, расчёт комиссии, курса и суммы зачисления.
- Для примера из PDF воспроизводится расчёт `500 ₽ → 51,65 TJS` при курсе `9,1 ₽/TJS` и комиссии `30 ₽` внутри суммы списания.
- После подтверждения доступны экран успеха, история операций и скачивание текстовой демо-квитанции.
- Баланс и история сохраняются в `localStorage` после перезагрузки страницы.
- Добавлены восстановление демо-баланса и отдельный сброс текущей формы.
- На компьютере показываются корпус телефона, навигация и сравнение с референсами; на мобильном приложение занимает весь экран.

## Backend и данные

### Поведенческий модуль

На Go реализован объяснимый статистический baseline, который:

- читает историю операций из PostgreSQL;
- учитывает только завершённые и уже зарегистрированные операции;
- находит регулярные поступления по клиенту, валюте и календарному дню;
- ищет первый трансграничный перевод в течение 0–3 дней после поступления;
- не смешивает валюты и платёжные коридоры;
- определяет компактное типичное временное окно с покрытием не менее 80% наблюдений;
- рассчитывает медиану и P25/P75 суммы перевода;
- исключает слабые, редкие и слишком широкие по времени паттерны;
- подавляет предложение, если перевод в текущем цикле уже выполнен;
- корректно работает с локальными часовыми поясами, переходом через полночь, DST и границами месяцев;
- сохраняет воспроизводимый срез кандидатов в `behaviour_push`.

Для демо подготовлено 64 синтетических операции за март–август 2026 года. Они включают регулярного, нерегулярного и недостаточно активного пользователей, а также неуспешные и внутренние операции для проверки фильтрации.

### Pusher

Реализован отдельный сервис доставки уведомлений:

- сначала рассматривается активный поведенческий сигнал;
- затем глобальные сообщения типа `history`;
- после них — сообщения типа `news`;
- на одного пользователя действует общий лимит: не более двух уведомлений за локальную неделю;
- блокировка строки пользователя и уникальные ограничения защищают от повторной доставки и гонок между воркерами;
- доставка записывается в `completed_push`;
- вместо внешней push-платформы используется локальный транспорт `demo-inbox`.

### API истории платежа

Добавлен `GET /api/behaviour/history`, который возвращает знакомый исторический перевод пользователя: получателя, телефон, банк, страну, назначение, валюты, сумму и число прошедших недель. Контракт предназначен для предзаполнения формы перевода.

Также доступен `GET /api/notifications` для просмотра доставленных демо-уведомлений.

### Payment Scheduler

Реализован сервис ежемесячных платежей:

- `POST /api/schedules` — создание после явного `confirmed: true`;
- `GET /api/schedules` — список расписаний;
- `GET /api/schedules/{id}` — получение одного расписания;
- `PUT /api/schedules/{id}` — изменение;
- `DELETE /api/schedules/{id}` — отмена;
- `Idempotency-Key` защищает от двойного создания;
- сохраняются исходный день месяца, локальное время и IANA timezone;
- в коротком месяце дата временно переносится на последний день, а затем возвращается к исходному числу;
- таблица `scheduled_payment_runs` не допускает повторного исполнения за одну плановую дату;
- вместо реального списания используется локальный `demo-ledger`.

### Инфраструктура

- Подготовлены миграции схемы PostgreSQL и повторяемое заполнение демоданными.
- Добавлены CLI-команды `migrate`, `seed`, `analyze` и `demo`.
- Настроен Docker Compose для PostgreSQL, Behaviour API, Pusher и Payment Scheduler.
- Сервисы публикуются только на localhost: `8080`, `8081` и `8082`; PostgreSQL — `5433` по умолчанию.
- Для API используется демонстрационный заголовок `X-User-ID`; в реальной системе его должен выставлять доверенный шлюз после аутентификации.

## Проверки

В проекте есть следующие уровни проверки:

- Node.js unit-тесты расчёта перевода, комиссии, лимитов, баланса, телефона и четырёх стран;
- Go unit-тесты поведенческого алгоритма, календарной логики и сервисного слоя;
- `go vet` для статического анализа Go-кода;
- PostgreSQL-интеграционные тесты миграций, идемпотентности, пересчёта срезов, приоритетов Pusher и Scheduler;
- Playwright-сценарии полного перевода, лендинга, пяти feature-страниц, ошибок ввода, сохранения истории, квитанции и мобильной адаптации;
- набор контрольных скриншотов в `reference/verification/`.

На момент подготовки этого документа локально выполнены и успешно пройдены:

```text
npm test          — 4/4 теста пройдено
go test ./...     — все доступные unit-тесты пройдены
go vet ./...      — замечаний нет
```

Интеграционный тест с PostgreSQL запускается отдельно с `TEST_DATABASE_URL`. Браузерные проверки требуют Playwright и Chromium.

## Как запустить

Веб-прототип:

```sh
npm run dev
```

После запуска он доступен по адресу <http://localhost:5173>.

Полное backend-демо:

```sh
docker compose up -d --wait db
docker compose run --build --rm behaviour demo --as-of 2026-09-01T00:00:00+03:00
docker compose run --build --rm behaviour seed-services
docker compose --profile services up --build
```

## Текущие ограничения

- Реальные переводы, банковская авторизация, проверка получателя и списание денег не подключены.
- Push-доставка и исполнение расписаний заменены локальными демо-адаптерами.
- Курсы, ML-сигналы, продуктовые метрики и Open Data синтетические.
- Поведенческий алгоритм является baseline: его качество и бизнес-эффект ещё нужно проверить на out-of-time выборке и в пилоте.
- Не реализованы праздничные переносы зарплаты, адаптация к смене поведения и потоковая обработка банковского масштаба.
- Перед промышленной отправкой уведомлений нужны согласия клиента, тихие часы, актуальная проверка курса и повторная проверка выполненного перевода.
- Веб-прототип и Go-сервисы демонстрируют единый продуктовый замысел, но пока не соединены прямыми frontend-to-backend запросами.

## Итог

Готов связный локальный прототип: от презентации пяти продуктовых идей и ручного трансграничного перевода до серверного анализа поведения, приоритизации уведомлений, получения истории знакомого платежа и управления регулярными платежами. Ключевые расчёты и backend-правила покрыты автоматическими тестами; внешние банковские и ML-интеграции намеренно оставлены за границами демо.
