# Alpha Remit Signal

Сигнальный слой для уведомлений о переводах из рублей в TJS, UZS, KGS, AMD и
KZT. Проект использует открытые дневные курсы ЦБ, нормированные до рублей за
одну единицу иностранной валюты. USD, EUR и CNY используются только как
контекстные признаки.

Финальное решение — boosting, который оценивает каждую опубликованную дату.
Hard-индикаторы не определяют дату отправки: они используются только как
проверяемое объяснение в тексте ML-пуша. Отдельно 5-го и 20-го формируются
нейтральные сервисные напоминания.

## Быстрый старт

Требуется Python 3.13.

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

В репозитории уже находится зафиксированный входной snapshot:

```text
data/processed/cbr_fx_daily_2010-01-01_2026-09-02.csv
```

Формат другого входного файла:

| Поле | Описание |
|---|---|
| `date` | дата публикации курса |
| `currency` | код валюты: AMD, KGS, KZT, TJS, UZS; для ML-контекста также USD, EUR, CNY |
| `rub_per_unit` | рублей за одну единицу иностранной валюты, положительное число |

Повторно скачать открытые данные ЦБ можно командой:

```bash
.venv/bin/python scripts/download_and_eda.py \
  --start 2010-01-01 \
  --end 2026-09-02
```

Для точного воспроизведения приведённых ниже результатов следует использовать
зафиксированный snapshot, а не более свежую выгрузку.

## Базовая задача: сигнальный слой

Этот сценарий закрывает пункты 1–5 ожидаемого результата: код, воспроизводимый
бэктест, матрицу индикаторов, цену ожидания, правило комбинирования и библиотеку
текстов. Backend и Docker для него не нужны.

### Полное воспроизведение

Запускать из корня репозитория в указанном порядке:

```bash
# 1. Честный walk-forward бэктест hard-индикаторов и итоговая матрица.
.venv/bin/python scripts/backtest_hard_signals.py \
  --input data/processed/cbr_fx_daily_2010-01-01_2026-09-02.csv

# 2. Замороженная ML-policy: обучение h=11, официальная оценка h=1/3/5/10/20.
.venv/bin/python scripts/backtest_ml_signals.py \
  --experiment cross-h-reproduction \
  --outer-start-year 2023

# 3. Коммуникационные ограничения и обязательные reminders 5/20.
.venv/bin/python scripts/backtest_ml_signals.py \
  --experiment calendar-reminders

# 4. Собрать итоговый отчёт по hard- и ML-сигналам.
.venv/bin/python scripts/build_ml_notebook.py

# 5. Отдельно посчитать цену ожидания hard-подтверждения.
.venv/bin/python scripts/backtest_ml_signals.py \
  --experiment waiting-cost
.venv/bin/python scripts/build_waiting_cost_notebook.py
```

Готовые отчёты:

- `notebooks/ml_signals_backtest.ipynb` — основной отчёт: hard-матрица,
  OOT-метрики ML, устойчивость, частота и кучность;
- `notebooks/waiting_cost_analysis.ipynb` — отдельный ответ на развилку быстрых
  и медленных индикаторов;
- `docs/push_text_library.md` — разрешённые шаблоны, реальные примеры,
  выключенные сценарии и запрещённые формулировки.

Чтобы заново выполнить все ячейки после сборки:

```bash
.venv/bin/jupyter nbconvert --to notebook --execute --inplace \
  notebooks/ml_signals_backtest.ipynb \
  notebooks/waiting_cost_analysis.ipynb \
  --ExecutePreprocessor.timeout=180
```

### 1. Код и сигнал на произвольную дату

Зафиксированная production-модель находится в
`models/ml_good_push_2026.joblib`, а её читаемый manifest — в
`models/ml_good_push_2026.json`. Bundle обучен только на исходах, созревших до
`2026-01-01`; при генерации сигналов модель повторно не обучается.

Воспроизводимое пересоздание bundle:

```bash
.venv/bin/python scripts/export_ml_model.py \
  --policy-year 2026 \
  --input data/processed/cbr_fx_daily_2010-01-01_2026-09-02.csv
```

Финальный inference-интерфейс принимает ряд курсов и дату среза:

```bash
.venv/bin/python scripts/generate_signals.py \
  --as-of 2026-08-04 \
  --input data/processed/cbr_fx_daily_2010-01-01_2026-09-02.csv
```

По умолчанию результат сохраняется в:

```text
data/processed/production_signals_2026-08-04.csv
```

Другой путь можно передать через `--output`. Если backend действительно может
предзаполнить сумму и реквизиты прошлого перевода, добавляется флаг:

```bash
.venv/bin/python scripts/generate_signals.py \
  --as-of 2026-08-05 \
  --input data/processed/cbr_fx_daily_2010-01-01_2026-09-02.csv \
  --output /tmp/signals.csv \
  --prefill-available
```

Без `--prefill-available` календарный пуш открывает обычную форму и не
утверждает, что данные уже заполнены.

#### Контракт выходной таблицы

| Поле | Смысл |
|---|---|
| `date` | дата отправки |
| `corridor` | коридор, например `RUB→TJS` |
| `indicator` | `ml_good_push` либо `calendar_5/calendar_20` |
| `direction` | выгодное направление для ML или `calendar_neutral` для reminder |
| `strength` | percentile ML-score от 0 до 1; для reminder не применяется |
| `speed` | средняя скорость за три публикации в bp; положительное значение означает движение курса в выгодную для перевода сторону |
| `recommended_scenario` | `favourable_now` или `scheduled_transfer` |
| `signal_source` | `ml` или `calendar_reminder` |
| `explanation_indicator` | причинный факт, использованный в тексте |
| `template_id` | ID согласованного шаблона из библиотеки текстов |
| `push_title`, `push_text` | готовые заголовок и тело уведомления |
| `currency`, `rub_per_unit` | валюта и последний известный ориентир ЦБ |

Расчёт причинный: функции сначала отбрасывают все наблюдения после `--as-of`.
Обучение использует только таргеты, успевшие созреть до соответствующего
walk-forward cutoff. В день без новой публикации прошлый ML-сигнал повторно не
отправляется. Это поведение покрыто тестами.

### 2. Отчёт по бэктесту

Hard-бэктест проверяет momentum, низкий уровень и выход из стабильного коридора
по каждому валютному коридору. Главный артефакт:

```text
data/processed/hard_signals/hard_indicator_corridor_report.csv
```

Он содержит матрицу `индикатор × коридор × hit rate × random hit × lift ×
benefit` и прямое решение по каждой строке.

Итог hard-части:

- ни одно hard-семейство не прошло одновременно требуемый устойчивый lift и
  положительную экономическую выгоду как самостоятельный trigger;
- momentum, low level и corridor exit down оставлены как причинные факты для
  текста уже выбранного ML-пуша;
- corridor exit up и сценарий «окно закрывается» исключены из финального потока.

Финальная ML-оценка — rolling yearly walk-forward: модель для 2025 года видит
только завершённую историю до 2025-го, модель для 2026-го может использовать
уже завершившийся 2025 год. Период 2025–2026 поэтому является объединением двух
OOT-fold, а не единым замороженным holdout.

После коммуникационных ограничений результаты на 2025–2026 до 5 августа 2026:

| h | Средний lift | Минимальный lift по валютам | Средняя выгода | Минимальная выгода | Benefit значим для всех валют |
|---:|---:|---:|---:|---:|:---:|
| 1 | 1.152 | 1.078 | +6.8 bp | +1.3 bp | Нет |
| 3 | 1.161 | 1.102 | +14.0 bp | +10.6 bp | Нет |
| 5 | 1.308 | 1.260 | +24.8 bp | +21.7 bp | Да |
| 10 | 1.481 | 1.352 | +51.5 bp | +41.4 bp | Да |
| 20 | 1.762 | 1.588 | +94.8 bp | +76.0 bp | Да |

Основной горизонт замороженной policy — `h=10`. Все пять горизонтов оценивают
одни и те же OOT-даты отправки и не используются для повторного выбора
победителя.

#### Определения метрик

Для сообщения «сейчас выгодно» попадание на горизонте `h`:

```text
truth_now(T,h) = 1[P_T <= min(P_T+1, ..., P_T+h)]
```

Случайный baseline использует даты того же валютного коридора и периода.

```text
lift_h = hit_rate_signal,h / hit_rate_random,h
benefit_bps(T,h) = (mean(P_T-h, ..., P_T+h) / P_T - 1) * 10 000
```

Для средней выгоды применяется односторонняя проверка
`H1: mean(benefit_bps) > 0` при `alpha=0.05` с календарно-месячным block
bootstrap. Календарные reminders не входят ни в числитель lift, ни в random
baseline, ни в benefit.

### 3. Быстрый или медленный индикатор

В `notebooks/waiting_cost_analysis.ipynb` сравниваются:

- быстрый вариант — отправить прошедший ограничения ML-пуш сразу;
- медленный — ждать до пяти публикаций первого hard-подтверждения.

Подтверждение появилось у 125 из 201 ML-сигнала. Медианная задержка составила
одну публикацию, p90 — четыре. Средняя цена ожидания среди подтверждённых
эпизодов равна `−41.6 bp`, то есть к подтверждению курс часто становился ниже.
Однако официальный lift ухудшился: на `h=5` с 1.308 до 0.964, на `h=10` с
1.481 до 1.144, а медианная частота сократилась примерно вдвое.

Решение для пилота: ML-пуш отправляется сразу. Более поздний hard-сигнал его не
задерживает; hard-факт используется в тексте только когда уже наблюдается в
дату ML-сигнала.

### 4. Правило комбинирования

Единый поток строится причинно и последовательно:

1. ML оценивает все опубликованные даты; hard-trigger не является gate.
2. На коридор сохраняется не более двух ML-пушей с понедельника по воскресенье.
3. ML-пуш следующего календарного дня после отправленного подавляется.
4. Из нескольких объясняющих фактов выбирается один: low level → corridor exit
   down → momentum → нейтральный текущий курс.
5. Ровно 5-го и 20-го добавляется отдельный сервисный reminder. Он не расходует
   ML-квоту и не утверждает выгодность момента.
6. При совпадении ML и reminder возвращаются две строки. Downstream-CRM может
   отправить их раздельно либо объединить, но финансовый и сервисный смысл в
   данных остаются разделены.

Финансовые метрики считаются только по ML-пушам после ограничений. Общая
частота ML + 5/20 составляет в среднем около 0.95 сообщения на коридор в неделю;
диапазон по валютам — примерно 0.88–1.01.

### 5. Библиотека текстов

`docs/push_text_library.md` содержит:

- шаблоны ML + low level, momentum и corridor exit down;
- нейтральный fallback;
- варианты календарных reminders с предзаполнением и без него;
- конкретные примеры готовых пушей;
- выключенный сценарий «окно закрывается»;
- запрещённые прогнозы, гарантии и инвестиционные формулировки с объяснением;
- чек-лист перед отправкой.

Текст сообщает только факты о настоящем и прошлом. ML-score не показывается
клиенту как вероятность будущего курса. Курс ЦБ называется публичным ориентиром,
а не курсом исполнения перевода.

## Задача со звёздочкой: прототип и сервисы

Этот сценарий демонстрирует пункты 6–8 кейса: текущий клиентский путь от пуша к
переводу, предзаполнение знакомого платежа и поведение сервисов при доставке.
Он использует готовый интерфейс из `backend/public`, Go-сервисы и PostgreSQL.

### Требования

- Node.js 18+ для интерфейса;
- Go 1.23+ для локальных тестов;
- Docker Desktop с Compose для PostgreSQL и сквозного сервисного сценария.

### 1. Запустить интерфейсный прототип

В первом терминале:

```bash
cd backend
npm run dev
```

Открыть:

- `http://localhost:5173/features/recommendation` — ML-пуш и путь до перевода;
- `http://localhost:5173/features/prefill` — предзаполнение знакомого платежа;
- `http://localhost:5173/features/behaviour` — поведенческий сигнал;
- `http://localhost:5173/features/scheduler` — регулярный перевод.

Интерфейс воспроизводит мобильный путь локально и не выполняет реальных
банковских операций.

### 2. Проверить Go-сервисы

```bash
cd backend/behaviour
go test ./...
go vet ./...
cd ../..
```

Для теста с настоящей PostgreSQL сначала поднять базу:

```bash
cd backend
docker compose up -d --wait db

cd behaviour
TEST_DATABASE_URL='postgres://behaviour:behaviour_demo@localhost:5433/behaviour?sslmode=disable' \
  go test ./...
cd ..
```

### 3. Поднять backend

Из каталога `backend`:

```bash
docker compose run --build --rm behaviour demo \
  --as-of 2026-09-01T00:00:00+03:00

docker compose --profile services up --build -d
```

После запуска доступны:

| Адрес | Назначение |
|---|---|
| `localhost:8080` | Behaviour API и приём ML-сигналов |
| `localhost:8081` | Pusher и inbox уведомлений |
| `localhost:8082` | Payment Scheduler |
| `localhost:5433` | PostgreSQL |

### 4. Передать временной ряд модели и отправить сигнал

Из корня репозитория:

```bash
ML_INGEST_TOKEN=demo-ml-token \
.venv/bin/python scripts/generate_signals.py \
  --as-of 2026-08-04 \
  --input data/processed/cbr_fx_daily_2010-01-01_2026-09-02.csv \
  --output /tmp/production_signals_2026-08-04.csv \
  --publish-url http://localhost:8080/api/ml-signals
```

Последовательность внутри команды:

1. загружается зафиксированный `models/ml_good_push_2026.joblib`;
2. из данных не позднее `--as-of` строятся причинные признаки;
3. модель оценивает даты без повторного обучения;
4. применяются frozen percentile threshold и коммуникационные ограничения;
5. только прошедшие ML-сигналы отправляются в `POST /api/ml-signals`.

Пример `2026-08-04` воспроизводимо создаёт кандидатов KGS и TJS. Календарные
напоминания 5/20 остаются отдельным CRM-потоком и в ML endpoint не отправляются.

### 5. Доставить и проверить notification

Pusher автоматически опрашивает базу каждые `POLL_SECONDS`. Для немедленной
доставки в демо:

```bash
curl -X POST \
  -H 'X-User-ID: demo-regular' \
  http://localhost:8081/api/pusher/tick
```

Получить inbox демопользователя:

```bash
curl \
  -H 'X-User-ID: demo-regular' \
  http://localhost:8081/api/notifications
```

Повторная публикация того же сигнала не создаёт дубль. ML-уведомление получает
только клиент с завершённым переводом в соответствующую валюту; затем Pusher
применяет общий лимит не более двух сообщений на пользовательскую неделю.

### 6. Остановить сервисы

```bash
cd backend
docker compose --profile services down
```

### Граница текущего прототипа

Go-контур `модель → PostgreSQL → Pusher → completed_push` реализован отдельно от
браузерной демонстрации. Карточка пуша во frontend использует детерминированную
локальную симуляцию того же клиентского пути; браузер пока не читает
`completed_push` через API. Это не влияет на бэктест или серверную доставку, но
для единого production UI потребуется заменить симуляцию запросом к Pusher API.

## Проверка тестами

```bash
PYTHONWARNINGS=ignore .venv/bin/python -m unittest discover -s tests
```

Проверяются, в частности:

- неизменность причинных признаков при изменении будущих цен;
- созревание train/validation таргетов до cutoff;
- единые даты сигналов при оценке разных `h`;
- недельный лимит и запрет соседних ML-дней;
- reminders ровно 5-го и 20-го;
- отдельные строки ML и reminder при совпадении даты;
- контракт production-таблицы и отсутствие повторной отправки в день без
  публикации.
